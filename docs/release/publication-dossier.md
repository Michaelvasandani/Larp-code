# larp-code publication dossier

Status: candidate package assembled by automation; publisher, privacy, rights,
and Chrome Web Store human review are intentionally not claimed here.

## Candidate identity

- Product: `larp-code`, popup-only Manifest V3 extension.
- Package version: `0.1.0` (from `package.json`).
- Build fixed point: `f7784af4ba812d45b529bbd02c492b8286decd6a`, the reviewed
  ticket34 and ticket36 prerequisite integration plus migration-order and RLS
  compatibility repairs.
- Candidate archive: produced by `pnpm publication:assemble` at
  `artifacts/ticket40-publication/larp-code-0.1.0.zip` when a release backend
  origin and publishable client key are supplied.
- Package digest: generated beside the archive as `candidate.sha256`; it must
  be copied into the publisher's release record after the final production
  build. A local Supabase build is not a publication candidate.

The archive records the exact generated candidate and its SHA-256. The
publishable client key is intentionally passed through the build environment
and is never committed. A Supabase `service_role` key, database password, mail
secret, scheduler secret, private key, or reusable review credential is
forbidden by the package checker.

## Single purpose and user-data disclosure

larp-code has one purpose: two adults can use a shared, time-bounded NeetCode
150 Challenge to record cooperative, self-attested progress and see the
derived shared Grovekin Pet condition. It does not detect browser activity,
scrape or fetch NeetCode/LeetCode, advertise, profile, sell data, send
reminders, or provide social moderation.

The public privacy policy is packaged at [`privacy.html`](../../src/privacy.html)
and linked from the product's Legal and About surface. It describes account,
Invitation, Challenge, Solve, local-storage, provider, retention, deletion,
security, and limited human-support access. Its public support route is the
repository issue page; it does not require a larp-code login.

## Exact permission and origin decision

The candidate manifest declares only `storage`. It has exactly one host
pattern, the HTTPS origin supplied as `SUPABASE_URL`, and `connect-src` permits
only that HTTPS origin and its corresponding WSS Realtime origin. There are no
content scripts, web-accessible resources, broad URL patterns, cookies, tabs,
webRequest, scripting, debugger, notifications, alarms, identity, or remote
code permissions. The worker owns the Supabase client and validates all
responses as data.

The permission and network checker reads the candidate itself. It rejects
local/development origins, host wildcards, undeclared URLs, LeetCode/NeetCode
traffic, remote scripts, dynamic code execution, source maps, secret-like
material, and missing policy/provenance surfaces.

## Review and release boundary

Automated checks prove package shape and source-grounded disclosure alignment;
they do not prove production deployment, provider configuration, publisher
identity, rights-holder approval, or human visual review. Those are explicit
open sign-offs in `human-review-checklist.md` and remain blockers until a
publisher supplies evidence. No reusable production credential is included in
this repository or in the archive.
